# Changelog

## 1.15.20 (TBD)

### Features
### Fixes

- [FIX][all] **A failed wallet recovery now tells you what went wrong instead of dropping you on an empty wallet.** Forgot Password wipes the local wallet before re-registering, but a failure during that re-registration was only written to the console and the app navigated on regardless — so you landed on a wiped wallet with no explanation, which looks exactly like losing your funds. The reason is now shown on the confirmation screen with a Retry, and the flow stays put instead of navigating away. (#630)

- [FIX][all] **Restoring from a seed phrase while the network is down no longer creates an empty wallet.** The restore looks your account up on chain, and a lookup that FAILED because the node was unreachable was treated the same as "this seed has no account" — so a connection problem mid-restore silently created a brand-new empty wallet and your real account simply didn't appear. Restore now stops with "Could not reach the Miden network to look up your account… please try again" and creates nothing. A seed that genuinely has no account still creates a new wallet as before. (#629)
- [FIX][all] **A rate-limited Guardian no longer kills your transaction.** When the Guardian answers `429 Too Many Requests` before a transaction is submitted, the send/swap/claim now returns to the queue and retries automatically — honouring the delay the Guardian asks for, within sane bounds — instead of failing outright and making you start over. Rate limits hit after submission still fail loudly, since the transaction may already be on chain, and the 30-minute queue cap remains the terminal limit. (#617)
- [FIX][extension] **Recurring stuck "Consuming" notes are fixed by moving the wallet's WASM engine off the extension service-worker thread.** Transaction execution, proving, syncing, and reads now run in a dedicated `chrome.offscreen` document, so a wedged operation can no longer freeze the service worker and strand notes mid-consume; each operation is bounded by its own deadline and a wedged one is torn down and safely retried. Behind `MIDEN_USE_OFFSCREEN_CLIENT` (extension only; mobile/desktop unaffected). (#260)

### Changes

- [CHANGE][ci] **Getting your password wrong is now tested against a real, funded wallet.** The unlock screen is the one you see most — the vault key only ever lives in the extension's service-worker memory, so every worker restart sends you back to it — yet no browser test had ever typed a *wrong* password into it. So the escalating lockout (three wrong tries disables the field for a minute, and it frees itself with no action from you) was only ever checked against a stand-in for the vault, never the real one. A new end-to-end test funds a wallet with an exact amount, claims it, locks it, gets the password wrong three times, and unlocks properly — checking along the way that the field is still usable after the first two tries (three really is the minimum), that the countdown starts inside the advertised minute and actually ticks, and that the lockout held for a full minute measured on the wallet's own clock. It then checks the balance is exactly what it was before the lock, which proves the password genuinely re-derived the key that decrypts your accounts rather than just proving a screen changed. Test-only; the app gains one test hook attribute and no behaviour change.

- [CHANGE][ci] **Generated Playwright output can no longer be committed by accident.** `.gitignore` enumerated `/test-results` and `/test-results-ios`, which silently missed the per-suite directories other configs write (`-android`, `-stress`) — three such files reached main this way. Replaced the enumeration with `/test-results*` so every suite's output is covered, including suites added later.

- [CHANGE][ci] **Fixed the iOS E2E claim wait, which could never succeed.** While the wallet sits on the transaction-progress screen waiting for a claim, nothing is mounted that refreshes the store's balances — that projection is only written by the poll inside the home/token screens. The claim wait polled it anyway, so it read a frozen number and timed out even when the consume had landed on-chain. It now drives the store's own `fetchBalances` action before reading, instead of navigating away (which would stop the mobile transaction driver).
- [CHANGE][ci] **The Playwright suite is lint-clean.** 316 accumulated ESLint problems across `playwright/` are fixed rather than tolerated. Almost all were formatting; the substantive ones were a closure in a retry loop capturing a mutable binding, a redundant regex escape, and Playwright fixtures declaring an empty destructuring pattern. The `self` references in service-worker `evaluate()` blocks are correct as written — `window` does not exist in that scope — so those carry a scoped disable with the reason instead of a rewrite.
- [CHANGE][ci] **Fixed an E2E assertion that failed working sends.** The three send specs asserted the sender was debited by reading their balance once, immediately after waiting on the *recipient*. The recipient seeing the note only proves it is on-chain — the sender's own balances projection settles separately — so under CI load the read sampled a vault that had not moved yet and reported `debited 0` on a transfer that had actually succeeded. The check now waits for the debit, and its timeout message distinguishes "never debited" from "still catching up".

- [CHANGE][ci] **A green E2E run now means more than it did.** Every PR is checked for assertion shapes that pass whether or not the wallet works — `expect(balance).toBeGreaterThan(0)` and `waitForBalanceAbove(0, …)` (true for the wrong token, the wrong amount, or a balance that was already non-zero), `waitForTimeout` over 2s (a bet on machine speed that surfaces as an unrelated failure further down the spec), and `expect()` inside an `if` branch (reports PASS when the feature never rendered, which is what the popup send/receive smoke tests were doing). The rules are AST-based, so the helper docs that quote these patterns to explain the ban are not themselves flagged. The 79 instances already in the suite are recorded per file in `playwright/e2e/eslint-rules/known-violations.json` and do not fail CI — the gate blocks *new* ones and the recorded counts may only go down, so the backlog is visible and shrinking rather than quietly growing. `yarn lint:e2e`. Test-only; no app behaviour changes. (#615 follow-up) The baseline is a true ratchet: a tree that is *cleaner* than the recorded budget now fails too, because every unused slot is room for a new unfalsifiable assertion to land green.
- [CHANGE][ci] **E2E failures now point at the step that actually broke.** Several page-object methods could succeed silently: a Chrome send that rendered an error screen was `console.log`ged and returned as if sent, a send whose submit button never detached was ignored on both Chrome and iOS, and an iOS claim that never produced a balance returned normally after its timeout. Each of those turned into a failure minutes later on the *recipient's* balance, so a broken send read as a broken delivery and cost real time to re-attribute. Those methods now throw where the flow actually stopped, quoting the on-screen text. iOS `unlockWallet` also asserts it reached the unlocked state (Unlock screen gone + store Ready) instead of returning after a fixed sleep. Harness-only; no app behaviour changes. (#615 follow-up)
- [CHANGE][ci] **The Chrome E2E harness now waits for the wallet to say it's done instead of guessing with a stopwatch.** Every sync in the harness slept a flat 3.5s and then read `chrome.storage.local` — but the service worker's sync is fire-and-forget, so on a slow testnet round the harness read the *previous* sync's data and drew conclusions from it (a note that had just landed looked like it hadn't, a claimed one looked unclaimed). It now waits for the service worker's `SYNC_COMPLETED` broadcast, which is emitted only after the sync data is persisted — the exact write the harness goes on to read. Eight other fixed sleeps (post-reload settles, claim-button renders, post-submit navigation, lock screen) were likewise replaced with the DOM or store state they were standing in for. Each wait keeps the old sleep as its timeout ceiling, so a run can only get faster, never slower; the sleeps that genuinely have no observable signal (a consume's head start after a Claim click) were deliberately left alone and are now labelled as such. Test-only. (#615 follow-up)
- [CHANGE][ci] **A localnet E2E run now reports every spec, and a spec that only passed on its retry is named out loud.** The hermetic per-PR suites stopped at the first failing spec, so a ~25-minute run answered one question and left the rest unknown — two broken specs cost two full runs to discover. Those suites (E2E_NETWORK=localhost: local, earn, swap, guardian, bridge-guardian) now report up to three independent failures per run instead of one — bounded deliberately, because letting every spec burn its full timeout could exceed the job budget and kill the run before it uploads any artifacts at all; the expensive live-network runs (devnet/testnet, real-testnet bridge) still stop at the first failure, since each spec there spends shared faucet funds and wall-clock. Separately, those jobs run with `--retries=1`, which quietly turned a real flake into a clean green tick: each job now prints a `FLAKY: <spec> — passed on retry N` line per retried-then-passed spec, so the flake rate is a number someone can read off the log instead of an invisible one. The retry budget itself is unchanged, and the new report can never fail a job.
- [CHANGE][ci] **Every failing E2E spec now leaves a diagnosable failure report, not just the two-wallet ones.** The harness's `report.json` — failure category, diagnostic hints, per-wallet state at the moment of failure, browser/service-worker errors, recent timeline — was produced in the second wallet's teardown, so any spec that never asks for a second wallet (the swap smoke and guardian fault specs, and the whole bridge and earn suites) failed with nothing but a Playwright stack trace, and a run that died while the first wallet was still launching produced nothing at all. Report generation now runs as an automatic per-test fixture, so every spec emits one regardless of how many wallets it used; each wallet still snapshots its own state while its page is alive, and the report is still written exactly once with the same shape the agentic mode and downstream tooling already read. Test-harness only. (#639)
- [CHANGE][ci] **The blockchain E2E suite now refuses to run a wallet built for a different network than the harness.** Bring-up only checked that `dist/chrome_unpacked/manifest.json` existed, so a leftover build from an earlier run — a testnet bundle, say — could be driven by the localhost (docker) harness: the miden-client CLI mints notes on one chain while the wallet syncs another. That run either burns 20 minutes and fails with product-shaped symptoms (notes never arrive, balances stay zero) or, worse, goes green without ever exercising the network it claimed to. The fixture now reads the `MIDEN_NETWORK` token actually baked into the built bundles and aborts before a browser is launched, naming the built network, the harness network and the rebuild command — and it also catches a half-rebuilt `dist/` whose service worker and UI disagree with each other. Test-harness only; no app behaviour change.
- [CHANGE][ci] **Two shipped behaviours were untestable because the E2E test-hook flag also switched them off.** `MIDEN_E2E_TEST` is supposed to only install the harness hooks, but it additionally forced onboarding to finish in-tab and made the wallet throw away any persisted endpoint override. So no E2E run has ever reached the Chrome side panel — the surface a real Chrome user spends the entire session in — or the developer endpoint-override flow, and a regression in either could ship unnoticed. Those two opt-outs now have their own build flags (`MIDEN_E2E_DISABLE_SIDEPANEL`, `MIDEN_E2E_DISABLE_ENDPOINT_OVERRIDES`), which the E2E build scripts set explicitly so every existing suite behaves exactly as it does today, while a new suite can keep the test hooks and still drive the real panel. No shipped build sets either flag, so app behaviour is unchanged. (#624 follow-up)
- [CHANGE][ci] **The balance-conservation invariant now actually runs.** `stress.spec.ts` has always asserted that the two wallets' combined balance is unchanged by a randomized send/claim run — the check that catches a note lost or minted from nowhere, which no single-wallet balance assertion can see — but no workflow ever executed it. Added a nightly localnet job that runs it with the strict flag set explicitly. Nightly and un-retried on purpose: it is adversarial by design, so a failure wants a human rather than a re-run. (#615 follow-up)
- [CHANGE][ci] **The E2E money specs now assert exact amounts.** Ten Chrome specs moved off `expect(balance).toBeGreaterThan(0)` onto exact base-unit assertions that name the token and check both sides of a transfer — the recipient credited by exactly N and the sender debited by at least N. Mints now assert the exact unconsumed-note total, and claims assert the vault went **up** by N *and* the pending total went **down** by N, which is what distinguishes a real claim from a note that was merely discovered. (#615 follow-up)
- [CHANGE][ci] **E2E money assertions can now actually fail.** Adds symbol-aware, base-unit balance primitives and transfer/claim/conservation assertions for the E2E suite. The existing `getBalance()` discards the token symbol it is given and adds *unconsumed* notes to the balance, so paired with `expect(balance).toBeGreaterThan(0)` it stayed true for a wrong-token, wrong-amount, or never-actually-claimed transfer. The new helpers keep spendable-vault and pending-note totals strictly separate, compare exact `bigint` base units, and assert both sides of a transfer. No behaviour change to the app. (#615 follow-up)
- [CHANGE][ci] **Paused the live bridge-out E2E while the Epoch solver declines to quote it.** Since 2026-08-12 the solver answers `200 OK` with `NO_QUOTE_AVAILABLE` for the throwaway faucet token this spec mints, and re-running the last green commit unchanged reproduces it — so it is an external change, not a wallet regression. The same bridge-out flow still runs on every PR against the hermetic fake allocator, and the AggLayer route still runs on main. Tracked in #627. (#627)
- [CHANGE][ci] **A failing bridge quote now says why.** The bridge E2E gated the Fast route on a `$` appearing in the fee, which is the same `—` placeholder whether the route wasn't a bridge, the token never loaded, or the quote service returned nothing — and would have passed on a `$0.00` from a missing price. It now waits for the quote to actually resolve and, on failure, reports the quote hook's own error string (which the app records and never surfaced) alongside the real Epoch HTTP status and body. Test-only. (#615 follow-up)
- [CHANGE][ci] **Stop the guardian-lifecycle E2E harness from failing runs that actually succeeded.** `claimAllNotes`/`claimNotesByGroup` billed their ~8-12s reload against the caller's drain budget, and the deadline is only checked between iterations, so a note that drained mid-iteration could expire the clock and fail a wallet that had in fact claimed it. Both now start the clock after the reload and share one tail that re-samples at the deadline, applying the same two-consecutive-zeros rule before failing. The failure dump also renders `status` by name and sorts by `initiatedAt`, so a Completed row no longer reads as in-flight. (#615)
- [CHANGE][all] **A completed transaction now records that it finished.** Successful rows kept whatever stage they were in when they completed — a finished key rotation stayed at "confirming", a finished Guardian claim at "guardian-synced" — so a finished transaction read as still running in diagnostics. Completion now stamps the terminal stage; failed rows still keep the stage they failed at. (#618)
- Add hidden developer endpoint configuration (7-tap the Welcome logo during onboarding) to override RPC / prover / note-transport / faucet / explorer / guardian endpoints and network ID; read-only view with reset-to-defaults in Settings.

### Fixes

- [FIX][all] **Transaction receipts stick around and claims get a proper one.** The Generating Transaction screen no longer auto-navigates home ~10s after completion — the success/failure receipt stays up until the user taps Done (or Hide). Claim (consume) transactions now render their own summary ("{amount} {symbol} → Consumed") and receipt: the note sender as "From", "Total Consumed" instead of "Total Paid", and a "Notes Consumed" row with the claimed note ids; the receipt's hash row is now labeled "Transaction ID" (was "Source TX") for all transaction types.
- [FIX][all] **Guardian provider names are spelled consistently across the wallet.** Onboarding, Settings, Activity and recovery now read each operator's display name from one canonical source, so "OpenZeppelin" and "LambdaClass" render the same everywhere (previously a mix of "Open-Zeppelin"/"Lambda Class"). (#464)
- [FIX][all] **A settled swap's order status no longer sticks on "Active" with a flickering spinner.** The order-tracking row reconciles the on-chain order lineage with the settlement this wallet has already observed: once the settlement (or reclaim) consume notes are seen locally, the status shows "Filled"/"Reclaimed" immediately, even if the lineage poll still lags behind reporting the order as active. The polling indicator is now tied to whether the order is genuinely still resolving rather than to each individual in-flight poll, so it no longer blinks off and on every couple of seconds while an order is active (most visible on iOS).
- [FIX][all] **Auto-consume no longer retries a permanently-unconsumable note forever.** The background auto-consume retry throttle was a sliding 30-minute window: old failures aged out, so a note that keeps failing on-chain every attempt (e.g. a deterministic kernel rejection the consumability check misses) dripped a fresh failed consume roughly every 5 minutes indefinitely — spontaneously reopening "Generating transaction", hammering the Guardian co-sign path, and piling up Failed rows in Activity. The throttle now counts a note's lifetime failures and backs off exponentially (5 min → 10 → 20 → … capped at 24 h), so a stuck note decays to at most a daily probe. It is a probe, not a permanent give-up: if the note later becomes consumable, the next attempt succeeds and it recovers on its own, and an explicit Retry still bypasses the backoff.
- [FIX][all] **A consumable note that fails to parse during sync is now logged instead of vanishing silently.** The sync parser dropped any note that threw mid-parse (corrupted metadata, an unexpected structure, a WASM-boundary issue) with a bare `catch`, so a note the user still owns on-chain would silently never appear — leaving them unable to see or report the missing funds. The failure is now logged (naming the note when its id was read) so a missing note is diagnosable; the note is still skipped for that sync and a later sync can complete it.
- [FIX][extension] **Recovering a wallet now opens in the side panel, matching first-run onboarding.** Creating a wallet handed off to the Chrome side panel on completion, but recovering an existing wallet (importing a seed with a Guardian, or the "forgot password" Guardian recovery) always finished in the onboarding tab instead. Both recovery flows now route through the same "Open wallet" handoff screen, so recovery opens in the side panel just like onboarding; non-extension builds and E2E keep the in-tab flow.
- [FIX][all] **A prover "missing procedure" mismatch is no longer misreported as a remote-prover timeout.** When the on-device prover rejects a transaction because it is missing a kernel procedure (a version/artifact mismatch between the app and its packaged prover — seen on Android as `… procedure with root digest 0x… could not be found`), the automatic remote→native fallback could relabel it as "Remote prover failed — please try again." That both hid the real cause and invited a retry that only re-fails on the same build. The transaction now shows a distinct message pointing at the app/prover version mismatch and noting that updating the app is what resolves it.
- [FIX][all] **A temporary proving-service outage no longer kills a transfer outright.** When a delegated (remote) transaction fails at the prove step — after the automatic local-proving fallback also can't complete — the transaction is now returned to the queue and retried with backoff instead of being marked Failed, so it completes on its own once the prover recovers (a proving-unavailable banner explains the wait, and the 30-minute queue cap remains the terminal limit). This is strictly a **pre-submit** recovery: a failure at the submit step is still terminal-failed, never retried, so a transaction that may already be on-chain can never be double-submitted. The failure message is also clearer — a provably pre-submit prove failure says the proving service was unavailable and no funds moved, while an ambiguous timeout says to check your balance before retrying — instead of a blanket "remote prover timeout, please try again."
- [FIX][all] **Token metadata fetched during sync is now persisted immediately.** Subsequent syncs reuse the existing metadata cache instead of repeatedly requesting the same faucet account from the node.
- [FIX][all] **A mistyped recipient address is rejected in the Send screen instead of failing after guardian approval.** Miden addresses are now validated with the SDK's full bech32 decode (`Address.fromBech32`) as you type, scan, or pick a contact — previously only the `mtst1`/`mm1`/`mdev1` prefix was checked, so a typo'd address sailed through to the transaction pipeline and surfaced as a bech32 error in Activity. A well-formed address for a different Miden network (e.g. a mainnet `mm1…` address on a testnet build) gets its own "different Miden network" message.
- [FIX][all] **The transaction-progress step durations no longer keep climbing after a step has finished.** Each step's elapsed time (e.g. "Guardian approved") was re-timed every time the underlying stage ticked — and because several stages map to the same visible step, a completed step's duration crept upward instead of freezing. Each step's start and end are now recorded exactly once, so the displayed durations settle the moment the step turns green.
- [FIX][extension] **Tapping a "note received" notification now opens the incoming-notes list instead of the wallet's QR/receive page.** The extension notification linked to the generic Receive screen, which told you nothing about the note that arrived; it now deep-links to Pending Notes, where the note and its claim action are shown — matching the mobile app's behavior. When Pending Notes is opened this way (in a fresh tab with no history), its back button now returns to the wallet home instead of doing nothing.
- [FIX][all] **The amount field now accepts a comma as the decimal separator.** On comma-decimal locales and keyboards (Spanish, German, French, …) typing `1,5` silently dropped the comma and became `15`, so you couldn't enter a fractional amount; the comma is now treated as the decimal point across Send, Swap, and Bridge.
- [FIX][extension] **A failed background sync-data write is no longer silent.** The extension's background sync wrote consumable notes and sync data to local storage without checking the result; if that write failed (e.g. storage quota exceeded) the error was swallowed and the wallet still signalled "sync complete", so open views could show stale or missing data. The write is now awaited, failures are logged, and the completion signal is only sent when the data actually persisted — the next sync retries.
- [FIX][mobile] **The "note received" notification no longer lingers after the note is auto-consumed.** Once the wallet auto-claims an incoming note, the "click to claim" notification is dismissed instead of staying around and opening to "nothing to claim" (on Android it previously had to be swiped away manually).
- [FIX][all] **The Swap screen now shows how much of a token you have available.** The "You Pay" field displays the spendable balance ("Available N TOKEN") so you don't have to leave the swap flow to check it.
- [FIX][mobile] **Passcode digits typed in quick succession are no longer dropped.** On the reveal/verify passcode screens, tapping numbers rapidly could register only the last digit; every tap is now captured.
- [FIX][all] **Production (minified) builds no longer crash on load with "React is not defined."** The SVG→React (SVGR) transform in the vite configs generated components with the automatic JSX runtime (importing nothing from `react`), but the bundler recompiles those `moduleType: 'jsx'` modules with the *classic* runtime (tsconfig `jsx: "react"`, which neither the `esbuild` nor `oxc` JSX options override in rolldown-vite) — emitting `React.createElement` calls against an undefined `React`. Harmless in unminified dev builds (a stray `React` leaked into the chunk) but every minified production build crashed on first render. SVGR now emits the classic runtime so each generated component imports `React`, matching the compile. Applied to the extension, mobile, and desktop configs.
- [FIX][all] **Private-note delivery no longer silently fails on fast chains.** The wallet relayed a private note's transport hint *after* waiting for the transaction to commit, so the hint (the client's sync height) could already be at or past the note's commitment block — the recipient scans forward from the hint and would never find the note. The note is now relayed *before* the commit wait (the SDK's prompt-relay flow), so the hint stays below the commitment block and the recipient picks the note up when it lands; the commit wait is preserved so `Completed` status still requires on-chain confirmation. Latent on testnet (slow blocks kept the sync height ≈ the commitment block at relay time); reproduced deterministically on a fast devnet.

## 1.15.18 (2026-08-05)

### Fixes

- [FIX][all] **The guardian picker no longer crashes when a guardian operator has no registered wordmark.** The Choose-Guardian screen asserted a logo entry for every option (`GUARDIAN_LOGOS[option.id]!`), so any guardian without a registered logo threw and blanked the screen; it now falls back to a generic avatar, mirroring the guardian-settings row's existing safe lookup.
- [FIX][all] **Assets on the Home page are ordered by fiat value.** The asset list keeps the native asset first, then ranks all other holdings by their current USD value from highest to lowest.
- [FIX][all] **Private notes now reliably arrive at their recipient.** Bumped the bundled web SDK (`@miden-sdk/miden-sdk`) to 0.15.9. Outgoing private notes are now relayed with a block hint so a recipient whose chain sync has advanced past the note's block still locates its on-chain commitment — previously such notes were silently dropped and never became consumable. This also pulls in miden-client 0.15.5's receive-side note-transport fixes (a transport delivery colliding with a note a local transaction is consuming no longer wedges sync; deliveries are validated on receipt).
- [FIX][all] **Dark-theme password and transaction screens keep their text and visibility icons readable.** Shared input labels, entered text, and icon slots now use theme-aware color tokens; both visibility-icon sets inherit the active text color instead of hardcoding black; and the transaction-processing helper no longer overrides its light/dark text token with the dark surface color. This fixes low-contrast unlock, reveal-key, send-processing, and swap-processing UI. (#430)
- [FIX][all] **A device-key rotation no longer intermittently leaves the new key unauthorized on the guardian.** After a hot-key rotation the wallet re-registers the new signer set on the guardian (this writes the guardian's request-auth allowlist); right after accepting the rotation delta the guardian can briefly reject that re-register while it canonicalizes. The old fixed 5×2s (~10s) retry budget could exhaust inside that window, silently leaving the new hot key unauthorized so every later request failed with a 401 "session expired". The re-register now retries with capped exponential backoff (~39s), comfortably clearing the canonicalization window.
- [FIX][mobile] **Bottom-sheet drawers no longer slide under the Android navigation bar.** The shared `DrawerContent` is `position: fixed; bottom: 0`, which anchors to the viewport — body's safe-area padding (mobile.html) never applies to fixed elements, so drawer CTAs (e.g. Guardian Settings' "Rotate Guardian") were clipped by the system nav bar. The drawer now pads itself with `env(safe-area-inset-bottom)` (0 on extension), and `GuardianInfoDrawer`'s per-instance workaround was removed to avoid double padding.
- [FIX][mobile] **Android launcher icon no longer renders as a cropped orange blob.** The adaptive-icon foreground PNGs drew the logo across ~66% of the canvas — right at the edge of the launcher's mask, so circular masks zoomed into the middle of the artwork. The foreground artwork is now scaled into the mask-safe area (~44% of the canvas, transparent padding), so the full logo shows inside the round/squircle mask.
- [FIX][mobile] **Seed-phrase screens block screenshots, and words are never cut off.** A new ScreenshotGuard plugin hides the seed phrase from screenshots/recordings while it's on screen (iOS secure-text-field layer trick, Android FLAG_SECURE) on the backup, reveal, verify, and import screens, the verify flow's word grid no longer truncates long words, and its note-down step gained a copy-to-clipboard button — so users copy/verify instead of saving a possibly-clipped screenshot. (#417)
- [FIX][all] **Imported seed phrases are cleaned up, and the verify-seed-phrase copy explains the procedure.** Typed or pasted seed words are now lowercased and stripped of stray whitespace (capitalized or padded words previously failed the wordlist check — this supersedes the earlier lowercase-only normalization), and a paste always fills exactly 12 slots. The verify-seed-phrase screens now say you'll note down the phrase and verify your knowledge by selecting its first and last words. (#445)

## 1.15.17 (2026-08-03)

### Fixes

- [FIX][mobile] **Bridge-in "Cross Chain" no longer hangs forever on "Preparing connection…" (iOS).** The native WalletConnect `configure` call passed `icons: APP_METADATA.icons`, but that shared `APP_METADATA` object is also handed to the web `@reown/appkit` modal (`createAppKit`), which wraps it in a reactive proxy in place — so `APP_METADATA.icons` is no longer a plain array. Capacitor's iOS bridge **silently drops** a plugin call whose arguments contain such a non-plain array, so `configure` never reached the native plugin and its promise hung forever, blocking `present()` and leaving the EVM connect stuck on "Preparing connection…". The arguments now pass a fresh plain array (`icons: [...APP_METADATA.icons]`), so the call serializes cleanly across the bridge. (The web E2E suite missed this because it drives the `connectUri` test hook, not the UI `configure` path.)

* [CHANGE][ci] **Guardian iOS E2E reads the on-chain auth structure with a pure storage parse instead of loading the multisig client.** The `verify_guardian_auth_structure` assertion's `__TEST_GUARDIAN_AUTH__` hook used to build a `MultisigService` (`getOrCreateMultisigService` → `MultisigClient.load`) and read it. Against the post-consume state — where the guardian's stored blob lags the on-chain account — that load entered a re-sign/realign loop (~48 `signWithHotKey` calls for this read vs. 26 for a full consume) that hung the single-threaded mobile WASM past the eval budget; the assertion never got far enough to run on iOS. - [FIX][all] **Consuming a note via the dApp API can no longer brick the wallet.** A dApp's `requestConsume` may carry serialized note bytes via `ConsumeTransaction`'s `noteBytes` parameter, which the wallet enqueues (`queueNoteImport`) and later imports via `NoteFile.deserialize` in `importAllNotes` (`src/lib/miden/activity/notes.ts`). That parameter has an undocumented, unvalidated requirement: it must be a serialized `NoteFile`. The natural thing for a dApp to pass — `note.serialize()` — produces a serialized `Note` instead (a different container, with no `"note"` magic header), so deserialization throws `notefile deserialization failed: invalid utf-8 sequence...`. The note itself is valid; only the serialization container is mismatched. (The companion fix below makes the wallet accept a `Note` here, so this specific mismatch no longer fails at all.) Previously `importAllNotes` aborted the whole batch on any failure and only cleared the persistent import queue (`miden-notes-pending-import`) after full success, so the bad note was retried on every transaction-loop iteration forever. Because `importAllNotes()` is the first call in `generateTransactionsLoop`, this permanently jammed ALL transaction generation (sends and consumes alike) — the queue lives in persistent storage, so the jam survived restarts and only a reinstall recovered. `importAllNotes` now imports each note independently (one failure no longer aborts the batch) and applies a bounded retry: a failing note is kept and retried, carrying an attempt count, and dropped only after `MAX_IMPORT_ATTEMPTS` (3) failures. This keeps the queue draining — a deterministically bad note can never loop forever and re-brick the wallet — while still giving genuinely transient failures (e.g. a `NoteFile::NoteId` import, which fetches the note over RPC and can hit a network blip) a chance to succeed, so a recoverable note (including a private note whose bytes are its only copy) isn't lost to a single blip. Processed-note removal happens inside the WASM lock and before `syncState`, so a sync failure can't leave processed notes queued for an unbounded retry. Queue entries gain an `{ bytes, attempts }` shape; legacy bare-string entries are normalized on read, so no migration is needed. Regression tests cover a failing note kept for retry with an incremented count, a poison note dropped after 3 attempts without `importAllNotes` ever throwing, the queue draining even when `syncState` throws, and concurrently-enqueued notes preserved across a pass. Now clears only the transactions table; a new `resetStorageDestructive()` preserves the full-wipe semantics for the options-page "Reset Wallet" button that actually wants it. (#187)
